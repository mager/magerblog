AI coding assistants are eager. Give them a vague prompt and they'll confidently build *something* — just maybe not the thing you needed. The bottleneck isn't the model. It's underspecification. Requirements that live only in chat history disappear the moment the session ends, and the next agent (or the next you) is back to guessing.

I hit this constantly. You describe a feature in a paragraph, the agent writes four hundred lines, and halfway through you realize it built the wrong thing. Fixing a misunderstanding in a one-paragraph proposal is free. Fixing it after four hundred lines is not.

[OpenSpec](https://openspec.dev) is the layer that sits between you and that moment. You agree on what to build before any code is written, and the agreement persists in your repo as living documentation. It's the thing I reach for now whenever a change has any real shape to it.

## What OpenSpec is

OpenSpec is an open-source spec-driven development (SDD) framework for AI coding assistants. Built by Tabish Bidiwale (Fission, YC W26) — ~65k GitHub stars, MIT licensed, npm `@fission-ai/openspec`. The thesis, in five words: **agree first, then build confidently.**

The whole thing is two folders in your repo:

```
openspec/
├── specs/              # source of truth — how the system behaves NOW
│   └── <domain>/
│       └── spec.md
└── changes/            # proposed updates — one folder per change
    └── <change-name>/
        ├── proposal.md
        ├── design.md
        ├── tasks.md
        └── specs/      # delta specs — what's CHANGING
```

`specs/` is what's true today. `changes/` is what you're proposing. When you finish a change, its deltas merge into `specs/` and the folder archives away. Two folders, one loop.

## The mental model

Five ideas, condensed:

**1. Specs are the truth.** A spec describes how your system behaves *right now* — requirements (RFC 2119: `MUST`/`SHALL`/`SHOULD`/`MAY`) plus concrete GIVEN/WHEN/THEN scenarios. It's the single agreed answer to "what does this software do?"

**2. A change is one unit of work.** One folder, one feature, holding the proposal, design, task list, and spec edits together. No archaeology through chat history.

**3. Delta specs describe the diff, not the world.** Inside a change you don't rewrite the whole spec — you write `## ADDED`, `## MODIFIED`, `## REMOVED`. This is the trick that makes OpenSpec work on a real codebase: you can specify a change to a 50,000-line app without first documenting everything. Most SDD tools assume greenfield. OpenSpec assumes brownfield.

**4. Artifacts are enablers, not gates.** The order `proposal → specs → design → tasks → implement` shows what becomes *possible* next, not what you're *forced* to do next. Discover the design was wrong mid-implementation? Edit it and keep going. Old-school spec processes are waterfalls; OpenSpec refuses that.

**5. Archiving folds the change back into truth.** Deltas merge into `specs/`, the change folder moves to `changes/archive/` with a date stamp. The cycle closes.

## The workflow, for real

This is the part I actually use day to day. I've been building a skills discovery portal with OpenSpec, and the loop has become muscle memory:

```
/opsx:explore → /opsx:propose → /opsx:apply → /opsx:sync → /opsx:archive
   (think)        (agree)         (build)       (merge)      (record)
```

Two command surfaces, and knowing which is which is the most common early stumble:

- `openspec ...` commands (like `openspec init`) run in your **terminal**.
- `/opsx:*` slash commands run in your **AI assistant's chat** — Claude Code, Cursor, Copilot, Codex, any of the 30+ tools it supports.

After `openspec init`, you live in chat. Here's what a real change looks like.

**Explore first.** When I'm not sure how to approach a change — say, adding a search/filter surface to the portal — I start with `/opsx:explore`. It's a no-stakes thinking partner: it reads the codebase, lays out options, names the tradeoffs, and sharpens a fuzzy idea into a concrete plan *before any artifact exists*. This is the single best habit for working with an agent that will otherwise confidently build the wrong thing. Skip it only when you already know exactly what you want.

**Propose.** Once the picture is clear, `/opsx:propose add-skill-search` drafts the whole plan in one step:

```
AI:  Created openspec/changes/add-skill-search/
     ✓ proposal.md — why and what
     ✓ specs/       — delta requirements + scenarios
     ✓ design.md    — technical approach
     ✓ tasks.md     — implementation checklist
     Ready for implementation!
```

The delta spec is plain Markdown — no special syntax to learn:

```markdown
## ADDED Requirements

### Requirement: Skill search
The system SHALL let users filter skills by free-text query,
matching against title, description, and tags.

#### Scenario: Partial match
- GIVEN a skill titled "Japanese Tutor"
- WHEN the user searches "japan"
- THEN the skill is returned in results
```

**Read it.** This is the step that matters and that nobody does with ad-hoc prompting: you actually read what the agent drafted. Tighten a vague `SHALL`. Delete a scenario that tests nothing. Add the edge case it missed — "make sure there's a scenario for an empty query returning all skills." It's plain Markdown. The agent covers what you point at; your job is to point at the right things.

**Apply.** `/opsx:apply` builds it, checking off tasks as it goes. If you discover the design needs adjusting mid-build, just update the artifact and continue — enablers, not gates.

**Archive.** `/opsx:archive` merges the deltas into `specs/`, moves the change to `changes/archive/2026-08-19-add-skill-search/`, and your specs now describe the new reality.

## The part I love most: the agent remembers

Here's what sold me, and it's not the "plan before you build" part — every framework promises that. It's that **the specs live in the repo as living documentation, so the agent has the history of every change and knows the current state.**

When I start a new session on the portal, the agent reads `openspec/specs/` and immediately knows how the system behaves today — not what it can infer from the code, but the *intent* behind it. When a change is archived, the delta becomes part of the truth and the archived folder is an audit trail of how we got there. Six months later, the spec tells me (and the next agent) why the system works the way it does.

That's the difference from tools that use requirements during planning and then throw them away. OpenSpec preserves the functional requirements behind your code. Context doesn't disappear when a chat session ends.

## How it compares

- **vs. [Spec Kit](https://github.com/github/spec-kit)** (GitHub) — thorough but heavyweight. Rigid phase gates, lots of Markdown, Python setup. OpenSpec is lighter, no Python required, ~5-minute setup vs 30, and you can iterate freely instead of being gated.
- **vs. [Kiro](https://kiro.dev)** (AWS) — powerful but you're locked into their IDE and limited to Claude models. OpenSpec works with the tools and models you already use.
- **vs. nothing** — vague prompts, unpredictable results, and an agent that confidently builds whatever you half-described.

## When it earns its keep (and when it doesn't)

OpenSpec adds a step. You write a short plan before building. The honest tradeoff:

**Worth it when** agreement matters — which turns out to be most of the time, once you're working with an agent that will confidently build whatever you vaguely asked for. Multi-step features, brownfield changes, anything where discovering the misunderstanding *after* four hundred lines would cost you.

**Not worth it** for a truly trivial one-line fix. Match the ceremony to the stakes. OpenSpec is lightweight but it isn't free.

Two usage notes worth knowing: OpenSpec works best with high-reasoning models (they recommend Codex 5.5 / Opus 4.7 for both planning and implementation), and it benefits from a clean context window — clear your context before starting implementation.

## The pattern

The whole design intent is consistent: planning and code live in the same repo, the artifacts are enablers not gates, and the spec layer persists as the agent's long-term memory of the system. You don't adopt OpenSpec to write code faster. You adopt it to decide what's worth writing — and to make sure the agent building it has the same picture you do, this session and every session after.

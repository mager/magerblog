OpenClaw rebranded on January 30, 2026. NanoClaw's first commit landed January 31 — a single file, `src/index.ts`, 457 lines, titled "Personal Claude assistant via WhatsApp."

The Cohens — Gavriel and Lazer — built the original OpenClaw. When OpenClaw pivoted away from its original shape, they didn't follow it. They stripped the concept to its essence and shipped something new under a new name, one day later. [NanoClaw](https://github.com/nanocoai/nanoclaw) is the thing OpenClaw used to be, minus everything that made OpenClaw complicated.

I [killed OpenClaw in June](/blog/2026-06-02-killing-openclaw/) specifically because it ran on Codex, not my Claude Pro subscription. Per-token billing to keep an always-on agent alive didn't make sense when I already had a $20/month subscription sitting there. So I ported everything to `claude --channels` and a `CLAUDE.md`. That held.

I've been meaning to write up NanoClaw since then, mostly to recommend it on the strength of that tiny codebase. Before publishing I went and counted.

## The codebase, actually counted

I cloned it this morning. `src`, excluding tests: **19,533 lines across 146 TypeScript files.** Counting tests and everything else in the tree, it's closer to 68,000.

The "700 lines, read it over a coffee" version of NanoClaw was real. It was real in February. It is not what you get when you clone it today.

I don't think that's a scandal, and I want to be careful not to write it as one. Growth from 457 lines to 19,000 bought real things: the initial commit spoke WhatsApp and nothing else, and the current tree supports WhatsApp, Telegram, Slack, Discord, Teams, iMessage, Matrix, Google Chat, Webex, Linear, GitHub, WeChat, and email through Resend. Thirteen integrations don't fit in one file. Neither does a permissions module, a container runner, and a router — which is roughly where the bulk now sits.

But it does mean the reason I was going to recommend it no longer applies. "You can audit the whole thing yourself" was the pitch. At 146 files you're auditing it the way you audit anything else: partially, on trust, starting with the parts that scare you.

The Anthropic Agent SDK is still the foundation, and NanoClaw is still a thin-ish opinionated layer on top rather than a novel architecture. If you've read the Anthropic docs it remains legible. Legible is a weaker claim than auditable, and it's the one that survives.

## One container per session

This is the part that holds up completely, and it's the reason I still think the project is worth your attention.

Every conversation runs in its own Linux container, and agents can only see what's explicitly mounted. When the session ends, the container goes away. No shared state between conversations, no lateral blast radius, no single compromised session reaching the host.

My current setup — `claude --channels` on a Mac mini — has no sandbox at all. The session runs as me, on my machine, with access to whatever I've given it. The allowlist and `CLAUDE.md` keep it reasonably contained, but if the agent does something unexpected, it does it on my actual machine. That tradeoff is fine for my use case; I understand the surface and I control what connects. It's still real.

NanoClaw's container model solves this at a different layer. The isolation is architectural rather than behavioral: you're not relying on the agent following instructions to stay contained, you're relying on the OS to enforce a boundary. That's a better class of guarantee, and notably it's the part of the project that got *more* solid as the codebase grew, not less.

## The honest catch

NanoClaw runs on the Anthropic Agent SDK, and the SDK bills per token. Not Pro, not Max, not subscription credits.

That's exactly the reason I left OpenClaw. OpenClaw ran on Codex and billed per token. I switched to `claude --channels` to get onto my subscription. Running NanoClaw would put me back where I started: an always-on agent charging me per message, on top of a subscription I'm already paying for.

So the conclusion I reached in February survives the recount, for a completely different reason than I expected. The codebase argument evaporated. The billing argument didn't.

## Who this is actually for

Developers starting fresh who need an agent that reaches users across a lot of messaging platforms. It's MIT-licensed, the container isolation is genuinely good, and thirteen integrations maintained by someone else is a real offer — that's the part you'd otherwise be building.

If you're already on `claude --channels` and happy, the switch cost is real and the gains are situational. If you need WhatsApp or Discord from day one, or you want OS-level isolation without rolling your own Docker setup, NanoClaw is probably the right call.

What I'd no longer tell you is that you can read the whole thing first.

## On simplicity in AI tooling

I was going to end this post by holding NanoClaw up as the counterexample — the project that went small while everything else in the ecosystem added surface area. The numbers took that ending away from me, which is more useful than the ending I wanted.

The honest version: a framework that talks to thirteen platforms, sandboxes each session, and manages credentials is not going to stay at 457 lines, and shouldn't. Small codebases aren't a virtue on their own. They're a snapshot of how much a project has been asked to do yet.

The thing worth keeping from the original pitch isn't the line count, it's the disposition — one process, few files, OS-level isolation instead of clever application-level permissions. NanoClaw still has that disposition at 19,000 lines. That's the part that was actually load-bearing.

I'll keep watching. If they add a subscription-compatible runtime path, I'll reconsider on the merits.

*Line counts measured against `main` on July 26, 2026. Numbers on a live project have a shelf life — count it yourself before quoting me.*
